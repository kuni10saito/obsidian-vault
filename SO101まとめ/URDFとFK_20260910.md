# URDF と順運動学（FK）

> **現在地**：この調査は [[SO101まとめ/IsaacLab_SO101_実機化]]（トラックB）の
> 「実機とシムの座標系が繋がらない」問題を解くために行った。
> 全体の位置づけは [[SO101_ノート地図_20260910]]、最上位は [[SO101_現状まとめ_20260909]]。

## 要約

- **URDF** はロボットの寸法と関節構造を書いたXMLファイル。**FKの入力データ**にあたる
- **FK（順運動学）** は「関節角度 → 手先の位置」を求める計算。行列の掛け算だけ
- URDFの `axis` 表記は**そのまま読むと間違える**。SO-101では6関節すべて `0 0 1` と書かれているが、実際の向きはバラバラで**2つは負**
- この罠が原因で、`SIGN[1]` と `SIGN[4]` の符号を長期間間違えていた
- **Isaac Sim を起動せず URDF から直接FKを計算**できる。1秒で済み、結果はIsaac Labと差分0.98mm以内で一致

---

## 1. URDF とは

**Unified Robot Description Format**。ロボットを「硬い部品」と「つなぎ目」の集まりとして記述するXML。ROSで標準化され、Isaac Lab / Gazebo / MuJoCo など主要なシミュレータが読める。

SO-101のファイル：

```
/home/saito/isaac_so_arm101/src/isaac_so_arm101/robots/trs_so101/urdf/so_arm101.urdf
```

385行。手元にもコピーがある（`Desktop/so101_rl/so_arm101.urdf`）。

## 2. 構成要素は2つだけ

### link（リンク）＝ 硬い部品

変形しない剛体。見た目のメッシュ、質量、慣性モーメントを持つ。

SO-101のリンク：

```
base_link, shoulder_link, upper_arm_link, lower_arm_link,
wrist_link, gripper_link, moving_jaw_so101_v1_link, gripper_frame_link
```

`gripper_frame_link` は**実体のない基準点**で、グリッパー先端の位置を表すために置かれている。FKで「手先の位置」と言うときはこれを指す。

### joint（ジョイント）＝ つなぎ目

「どの部品」と「どの部品」を、「どこで」「どの軸回りに」繋ぐか。主な属性：

| 属性 | 意味 |
|---|---|
| `type` | `revolute`（回転）／`fixed`（固定）など |
| `parent` / `child` | 繋ぐ2つのリンク |
| `origin xyz` | 親フレームから見た**位置**（平行移動） |
| `origin rpy` | 親フレームから見た**姿勢**（回転） |
| `axis` | **そのジョイントのフレームでの**回転軸 |
| `limit lower/upper` | 可動範囲[rad] |

## 3. SO-101 の骨格

```
base_link ──73.5mm──▶ shoulder_link      (shoulder_pan)
          ──64.8mm──▶ upper_arm_link     (shoulder_lift)
          ─116.0mm──▶ lower_arm_link     (elbow_flex)
          ─135.0mm──▶ wrist_link         (wrist_flex)
          ──63.7mm──▶ gripper_link       (wrist_roll)
          ──98.4mm──▶ gripper_frame_link (固定)
```

`distance` は各ジョイントの `origin xyz` のノルム。単純な直列リンク（枝分かれは `moving_jaw` のみ）。

### 可動範囲（URDF）

| 関節 | 範囲[rad] | 角度 | カウント換算 |
|---|---|---:|---:|
| shoulder_pan | −1.920 〜 +1.920 | 220.0° | 2503 |
| shoulder_lift | −1.745 〜 +1.745 | 200.0° | 2276 |
| elbow_flex | −1.690 〜 +1.690 | 193.7° | 2203 |
| wrist_flex | −1.658 〜 +1.658 | 190.0° | 2162 |
| wrist_roll | −2.744 〜 +2.841 | 320.0° | 3641 |
| gripper | −0.175 〜 +1.745 | 110.0° | **1252** |

換算は `カウント = rad × 4096/(2π)`（1rad ≒ 651.9カウント）。

## 4. ★最重要：`axis` の表記を読んではいけない

SO-101の全ジョイントは、URDF上 **`axis = "0 0 1"`（Z軸）** と書かれている。
しかし**親フレームでの実際の向きは違う**。

| 関節 | URDF表記 | 原点の `rpy` | **実際の軸** |
|---|---|---|---|
| shoulder_pan | `0 0 1` | [3.142, 0, −3.142] | **[0, 0, −1]** ⚠️ |
| shoulder_lift | `0 0 1` | [−1.571, −1.571, 0] | [0, +1, 0] |
| elbow_flex | `0 0 1` | [0, 0, 1.571] | [0, 0, +1] |
| wrist_flex | `0 0 1` | [0, 0, −1.571] | [0, 0, +1] |
| wrist_roll | `0 0 1` | [1.571, 0.049, 3.142] | [0, +1, 0] |
| gripper | `0 0 1` | [1.571, 0, 0] | **[0, −1, 0]** ⚠️ |

`shoulder_pan` は `rpy` に180度の反転（3.142 rad ≒ π）が入っているため、
**`+Z` と書いてあるのに実際は `−Z` 回りに回る**。

> **教訓**：URDFの `axis` は「そのジョイント固有のフレーム」での軸であって、
> 世界座標やロボット基準の軸ではない。`origin rpy` を掛けて初めて実際の向きが出る。
> **見ても読んでも分からない。行列を掛けるしかない。**

これが 2026-09-10 に `SIGN[1]` と `SIGN[4]` の誤りを発見した直接の原因。
過去に「構造から考えれば分かる」として推論し、間違えた経緯がある
（[[SO101まとめ/IsaacLab_SO101_実機化]] に記録）。

## 5. FK（順運動学）の計算

### 考え方

各ジョイントを**同次変換行列** `T`（4×4）で表し、根元から順に掛けるだけ。

```
T_joint = Translate(origin.xyz) · Rotate(origin.rpy) · Rotate(axis, q)
T_総合  = T_pan · T_lift · T_elbow · T_wristflex · T_wristroll · T_gripperframe
先端位置 = T_総合 の右上3成分
```

`Rotate(axis, q)` は**ロドリゲスの回転公式**：

```
R = I + sin(q)·K + (1−cos(q))·K²
K = | 0    −az   ay  |
    | az    0   −ax |     （軸ベクトルの歪対称行列）
    | −ay   ax   0  |
```

`rpy` の合成順は URDF 仕様で **Z·Y·X**（固定軸 roll-pitch-yaw）。ここを間違えると全部ずれる。

### FK と IK の違い

| | 入力 | 出力 | 解 |
|---|---|---|---|
| **FK** 順運動学 | 関節角 | 手先位置 | **必ず1つ**。行列を掛けるだけ |
| **IK** 逆運動学 | 手先位置 | 関節角 | 複数あることも、無いこともある。反復解法が必要 |

FKは常に安全に使える。今回のように「シムでは関節を+方向に回すと手先はどちらへ動くか」を
調べる用途には、FKだけで足りる。

## 6. 自前FK実装（Isaac Sim 不要）

### なぜ必要になったか

Isaac Lab の `fk_oracle.py` は正確だが**起動に数分**かかる。
2026-09-10 には **15分間 CPU 0% でハング**した（`ps` の状態 `S`、CPU 0.0%）。
過去にも1時間ハングして `timeout 400` を無視した記録がある。

URDFに同じ幾何情報が入っているので、直接読めば**1秒**で済む。

### 実装

`Desktop/so101_rl/urdf_fk.py`。numpy と標準ライブラリだけ。

### 検証結果（2026-09-10）

Isaac Lab の出力（`/tmp/fk_signs.log`）と同じ入力で比較：

| 摂動 | 自前FK Δ(X,Y,Z) | Isaac Lab Δ(X,Y,Z) | 最大差 |
|---|---|---|---:|
| pan+0.2 | [+0.0224, −0.0659, −0.0000] | [+0.0214, −0.0658, +0.0000] | 0.98mm |
| lift+0.2 | [+0.0325, +0.0153, −0.0675] | [+0.0321, +0.0157, −0.0674] | 0.40mm |
| elbow+0.2 | [+0.0157, +0.0074, −0.0536] | [+0.0155, +0.0076, −0.0538] | 0.23mm |
| wrist_flex+0.2 | [+0.0014, +0.0007, −0.0318] | [+0.0016, +0.0008, −0.0315] | 0.28mm |
| wrist_roll+0.2 | [+0.0004, −0.0012, +0.0010] | [+0.0004, −0.0012, +0.0010] | 0.05mm |

**差分は最大0.98mm で一致。**

> ⚠️ **絶対位置は約5mmずれる。** これは基準フレームの定数オフセット
> （Isaac Lab側が別の基準点を使っている）。
> **最初これを見て「自前FKは信用できない」と判断したが、それは誤り**だった。
> 符号判定や相対移動に使う分には影響しない。
> **検証するときは、用途に合った量（この場合は差分）で比べること。**

### 使い方

```bash
cd C:/Users/saito/Desktop/so101_rl
```

## 7. 実機との対応

サーボは 0〜4095 の整数（12bit）、シムはラジアン。変換式は
`so101_rl_deploy.py` の `rad_to_servo` / `servo_to_rad`：

```python
servo = SERVO_AT_DEFAULT[j] + SIGN[j] * (angle − DEFAULT_JOINT_POS[j]) * COUNTS_PER_RAD
```

- `COUNTS_PER_RAD = 4096/(2π) = 651.899`
- `SERVO_AT_DEFAULT` … シムのデフォルト姿勢に対応する実機のraw値（＝`HOME_POSITION` と仮定している。**この仮定自体は未検証**）
- `SIGN` … シムの角度が増えるとき、実機のrawが増えるか減るか

**`SIGN` こそが「URDFの軸の向き」と「サーボの回転向き」を橋渡しする値**。
URDFを読んでも決まらず、実機を動かして実測するしかない。

### 2026-09-10 に実測で確定した SIGN

| 関節 | 従来のコード | **実測値** | 判定方法 |
|---|---|---|---|
| M1 shoulder_pan | +1 | **−1** ❌誤り | 較正データ＋FK＋カメラ画像 |
| M2 shoulder_lift | +1 | +1（暫定） | 口頭の向き申告 |
| M3 elbow_flex | +1 | +1（暫定） | 口頭の向き申告 |
| M4 wrist_flex | +1 | **−1** ❌誤り | 実測姿勢FK＋カメラ画像＋感度検証 |
| M5 wrist_roll | +1 | **未確定** | 位置がほぼ動かず、姿勢で見る必要あり |
| M6 gripper | — | 開＝raw増加 | 全開3592／把持2346／全閉1854 |

## 8. 測定方法：言葉を使わない

「右へ動かして」「下げて」という指示は、**視点の取り違え**を生む。
実際、この件では過去に「右左はどちらから見るか」で混乱している。

そこで `joint_check.py` は次の方式をとる。

1. 動かす**前**のカメラ画像（2台）と全関節のraw値を記録
2. 「**どちらでもいいので**その関節だけ大きく動かして」と依頼
3. 動かした**後**の画像とraw値を記録
4. **どちらへ動いたかは、画像を見る側が判断する**

これで視点の食い違いが原理的に起きない。

### さらに：姿勢依存に注意

`shoulder_lift` や `elbow_flex` は、腕がどんな姿勢でも
「+方向に回すと手先が下がる」が概ね成り立つ。

しかし **`wrist_flex` は腕の姿勢によって上下が逆転する**。
だから基準姿勢のFK結果をそのまま当てはめてはいけない。
**実測したその姿勢そのもの**でFKを回して比較する必要がある。

`urdf_fk.py` が1秒で動くので、これが現実的になった。

### 感度検証

推定に不確かさがある場合（他の関節の値が正確に分からない等）は、
**乱数で揺らして多数回試す**。

M4の例：他の関節を±300カウント（±26°）揺らして1000回試行した結果、
観測（先端が上がった）と一致したのは `SIGN[4] = −1` が **80.4%**、
`+1` は **1.9%**。42倍の差で、推定誤差に対して頑健と判断した。

## 9. 見つかった食い違い

### グリッパーの開き幅

| | 幅 |
|---|---:|
| URDF（シム） | 110.0° = **1252カウント** |
| 実機の実測（1854〜3592） | **1738カウント** |

**実機はシムのモデルより486カウント（43°）広く開く。**

シムで「全開」の状態が、実機では**開ききっていない**ことになる。
4cmキューブを掴む際の余裕に効く可能性があり、要検証。

なお符号測定でグリッパーを動かしたとき Δ=**1252** ちょうどで、
URDFの範囲と完全に一致した。偶然かもしれないが、記録しておく。


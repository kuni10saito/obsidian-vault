# シミュレーションと実機をつなぐ — SO-101 で 56mm の誤差を見つけるまで

安価なロボットアーム **SO-101** を使い、シミュレータ（NVIDIA Isaac Lab）で学習した動きを
実機で動かそうとした記録。**一週間止まっていた原因が、誰も測っていなかった4つの数値だった**という話。

---

## 1. 何をしようとしていたか

やりたいこと自体は単純。

> **机の上の4cm木製ブロックを掴んで、カップに入れる。**

ただし方法が2つある。

| | トラックA：模倣学習 | トラックB：強化学習 |
|---|---|---|
| やり方 | 人がリーダーアームで操縦し、数十回繰り返して学習 | シミュレータの中で試行錯誤して学習 |
| 状態 | **実機で成功済み** | **掴めない** |

同じロボット、同じタスク。なぜ片方だけ動かないのか。

---

## 2. 決定的な違いは「翻訳」があるかどうか

### トラックA（模倣学習）は翻訳しない

人が操縦したときの**サーボの数値**（0〜4095の整数）を記録し、
**サーボの数値**を出力するように学習する。

```
カメラ画像 ＋ 現在のサーボ値 → 次のサーボ値
```

**シミュレータの座標系を一度も経由しない。** だから変換の誤りが入り込む余地がない。

### トラックB（強化学習）は翻訳が要る

シミュレータの中の世界は**メートルとラジアン**。実機は**0〜4095のカウント**。
両者を対応づけないと、学習した動きを実機で再現できない。

```
サーボ値 = 基準値 + 符号 × (シムの角度 − 既定角度) × 係数
```

この式には3つの数が要る。

| | 意味 | 決め方 |
|---|---|---|
| 係数 | カウント↔ラジアンの比 | 数学的に決まる（4096 ÷ 2π） |
| **符号** | 回転の向きが同じか逆か | **実機で測るしかない** |
| **基準値** | シムの原点に対応するサーボ値 | **実機で測るしかない** |

**この翻訳層こそが、トラックB固有の難所だった。**

---

## 3. 見つかった誤り

### 符号が2つ逆だった

ロボットの形状定義ファイル（URDF）を読むと、6関節すべてが `axis="0 0 1"`（Z軸回り）と
書いてある。**しかし実際の回転軸は違う。**

| 関節 | URDFの表記 | 親フレームでの実際の軸 |
|---|---|---|
| shoulder_pan | `0 0 1` | **[0, 0, −1]** ← 逆 |
| shoulder_lift | `0 0 1` | [0, +1, 0] |
| elbow_flex | `0 0 1` | [0, 0, +1] |
| gripper | `0 0 1` | **[0, −1, 0]** ← 逆 |

各関節は「原点の回転（rpy）」も持っており、`shoulder_pan` には180度の反転が入っている。
**`+Z` と書いてあるのに実際は `−Z` 回りに回る。**

> **教訓**：URDFの `axis` は、そのジョイント固有のフレームでの軸。
> 世界座標での向きではない。**読んでも分からない。行列を掛けるしかない。**

### 基準値が4つとも間違っていた

こちらが本丸。`SERVO_AT_DEFAULT`（シムの原点に対応する実機の値）に、
**`HOME_POSITION` をそのまま流用**していた。

作業メモには、HOME値の根拠がこう書かれていた。

| 関節 | HOME値 | 備考欄 |
|---|---:|---|
| shoulder_pan | 1505 | 「25度ズレ補正済み」 |
| shoulder_lift | 2242 | 「+10度が最適」 |
| elbow_flex | 1400 | **「アプローチ感」** |
| wrist_flex | 2375 | 「+30度」 |

**4つとも、模倣学習のタスク用に人が感覚で調整した値だった。**
シミュレータの原点とは何の関係もない。それを原点として使っていた。

実測した結果がこちら。

| 関節 | HOME値 | 実測した基準値 | 差 |
|---|---:|---:|---:|
| shoulder_pan | 1505 | **1409** | −96 |
| shoulder_lift | 2242 | **2197** | −45 |
| elbow_flex | 1400 | **1210** | −190 |
| wrist_flex | 2375 | **2044** | −331 |

**同じ指令に対する手先位置の解釈が、56mm ずれていた。**
未解決だった誤差予算「1.5〜2cm」の3倍以上。

---

## 4. どう測ったか

### 定規で測れる

特別な装置は要らない。**URDFから各関節軸の高さを計算し、テーブル面から定規で測って
突き合わせる。** アームを動かす必要もない。

| 測る点 | 物理的な目印 |
|---|---|
| shoulder_pan 軸 | ベース回転部の中心 |
| shoulder_lift 軸 | 2番目のモーターの回転中心 |
| elbow_flex 軸 | 3番目のモーターの回転中心 |
| wrist_flex 軸 | 4番目のモーターの回転中心 |
| 爪の掴む点 | 2本の爪の間 |

**根元から順に測ると、どこで誤差が入るかが特定できる。** 実際、肘の軸までは
予測と ±5mm で一致し、**その先が一斉に45〜60mm低かった**。

### ★ここで一度失敗した

高さを8点測って当てはめ、「較正できた」と考えた。**誤りだった。**

**高さは水平方向を拘束しない。** 当てはめは「高さが合う」パラメータを見つけたが、
水平は **56mm ずれたまま**だった。高さだけ完璧に合い、水平だけ大きく外れる——
不自然に見えて、実は当然の帰結だった。

較正済みカメラで**爪の水平位置を1点測って加えた**ところ、**4関節すべてが決まった**。

> **教訓**：3次元の対応づけを、1方向の測定だけで検証してはいけない。

### 結果

| | 水平誤差 |
|---|---:|
| 較正前 | **56 mm** |
| 高さだけで較正 | 56 mm（**改善せず**） |
| 水平を加えて較正 | **5〜7 mm** |

## 5. 測り方の工夫

### 「右」「左」と言わない

向きの確認で何度も混乱した。「カメラから見て右」なのか「ロボットから見て右」なのか、
言葉では決まらない。

そこで**言葉を使わない方法**にした。

1. 動かす**前**のカメラ画像と全関節の数値を記録
2. 「**どちらでもいいので**その関節だけ大きく動かして」と依頼
3. 動かした**後**の画像と数値を記録
4. **どちらへ動いたかは、画像を見る側が判断する**

これで視点の食い違いが原理的に起きない。

### 印ではなく輪郭を描く

キューブの位置を記録するとき、点で印をつけると **14mm ずれた**。

カメラの変換はキューブ中心の高さ（20mm）で較正してある。
**テーブル面（0mm）の印を同じ変換で読むと、系統誤差が入る。**

```
カメラ
   \
    ● 高さ20mm  ← 較正はここ基準
     \
      ● 高さ0mm ← 印はここ。同じ画素でも座標が違う
```

**底面の輪郭をなぞる**方式に変えた。輪郭は「キューブをはめる型」としてしか使えないので、
誤って座標を測ることがない。**座標は常にキューブを置いて測る。**

### 照明で精度が変わる

逆光のとき、検出面積が **3085 → 1191** に落ち、位置が **8mm** ずれた。
照明を点けると面積が戻り、位置も安定した。

NVIDIA の Sim-to-Real 教材が「ライトボックス」を要求する理由が、実地で分かった。

## 6. まだ解けていない問題

### 逆運動学が「向き」を扱っていない

「爪をこの位置へ」とは指定できるが、「爪をこの**向き**で」が指定できていない。

位置が数mm合っても、**爪の開閉面がブロックを挟める向きでなければ掴めない。**
実際、位置誤差5〜7mmまで追い込んでも把持は成立しなかった。

### モーターのトルクが足りない

肘に指令を出しても、**自重に負けて手前で止まる。**

| 指令 | 実測 | 不足 |
|---|---:|---:|
| 1406 | 1502 | 96 |
| 1340 | 1491 | **151** |
| 1554 | 1586 | 32 |

しかも**負荷によって変動する**ので、固定値では補正できない。
肩を17mm持ち上げても、肘が同じだけ沈んで**正味ゼロ**という場面もあった。

**これはソフトウェアでは解けない。実機の能力の問題。**

---

## 7. この経験から言えること

### パイプラインが動くことと、正しいことは違う

検出も推論も送信も同期も、すべて「動いて」いた。ログにもエラーは出ない。
**それでも掴めなかった。** 入力の数値が間違っていたから。

### 指標が誤りを検出できないことがある

同期制御の「追従誤差16〜35カウント」を品質指標として見ていた。
しかしこれは**「サーボが指令値に到達したか」**を測る指標で、
**符号が逆でも実機は逆向きの指令に忠実に追従する**。
**指標が構造的に盲目だった。**

### 根拠のない前提は、いつか必ず効いてくる

`SERVO_AT_DEFAULT = HOME_POSITION` は、誰も検証していなかった。
コードにも「【仮定】実機のHOME姿勢 = シムの default_joint_pos とみなす」と
書いてあった。**書いてあったのに、確認されないまま数週間使われた。**

### 測る対象を間違えると、測らないより危険

高さ8点という「充実した測定」をして、較正できたと判断した。
**測っていない方向に、56mmの誤差がそのまま残っていた。**

## 8. 使ったもの

| 道具 | 用途 |
|---|---|
| **定規** | 関節軸の高さ。特別な装置は不要 |
| **較正済みカメラ**（誤差9.1mm） | 水平位置 |
| **URDF から自作した順運動学** | 予測値の計算。1秒で動く |
| スマートフォン（不採用） | 傾斜計を試したが、基準が曖昧で使えなかった |

Isaac Lab を順運動学の計算機として使うこともできるが、**起動に数分かかり、
一度15分ハングした**。URDF を直接読んで行列を掛ければ**1秒**で同じ答えが出る
（Isaac Lab の出力と差分0.98mm以内で一致を確認）。

## 9. 現在地

| 項目 | 状態 |
|---|---|
| 座標変換の基準値 | ✅ 実測で確定（56mm → 5〜7mm） |
| 回転方向の符号 | ✅ 2関節の誤りを修正 |
| グリッパーの開閉値 | ✅ 実測値に修正（754カウントずれていた） |
| 爪がブロックに届くか | ✅ 届く・接触する |
| **把持の保持** | ❌ **未達**（向きと力の問題） |
| 学習したポリシーの実行 | ⬜ 未着手 |

**「なぜ届かないか分からない」から「位置は合った。残るは向きと力」まで来た。**
問題が一段具体的になった、というのが現時点の成果。

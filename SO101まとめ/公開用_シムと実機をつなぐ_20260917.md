# Claude Codeで Isaac Sim（7）シムと実機をつなぐ — 7つの基準のずれを潰す

**記事(4)(5)(6)の続き。** 前回までで、実機データによる模倣学習は成功した。
今回は**もう一方の道**——シミュレータで学習させた動きを実機に載せる——を進めた記録。

結論から言うと、**まだ掴めていない**。ただし原因は6つ見つかり、5つは潰れた。

---

## 前回まで

| 記事 | 到達点 |
|---|---|
| (4) | GR00T を実機データで学習 → **pick→place が30Hzで自律動作** |
| (5) | 合成データ＋Cosmos で Sim2Real を試行。カメラがタスクを写していない事故 |
| (6) | **6か月続いた「掴めるが迷走する」問題を解決**。実機で完璧に成功 |

(6)で分かった原因は、**学習データのカメラ位置がエピソード間でバラバラだった**こと。
同じ画像が違うロボット位置に対応する矛盾したデータで学習していた。
一貫した31本（cluster0）に絞って再学習したら、一発で成功した。

そこで掲げた原則がこれだった。

> **収集環境と評価環境を一致させ、失敗を1つずつデータで潰す**

---

## 今回：もう一本の道

同じロボット、同じタスク（4cm木製ブロックを掴む）を、
**Isaac Lab のシミュレータで強化学習**させて実機に載せる。

なぜわざわざ。模倣学習には限界があるからだ。
記事(6)で成功したモデルには**位置的なスイートスポット**がある。
31本すべてがほぼ同じ場所にブロックを置いて収録されたためで、
少しずれると失敗する。**教えた場所しかできない。**

シミュレータなら、何千通りもの配置を自動で試せる。
学習時間は35分。データ収集の手間がない。

---

## ところが、動かない

シム内では一貫して掴める。実機に持っていくと掴めない。

**なぜ模倣学習は動いて、強化学習は動かないのか。**

### 決定的な違いは「翻訳」の有無

| | 模倣学習 | 強化学習 |
|---|---|---|
| 学習するもの | **サーボの数値 → サーボの数値** | シムの関節角（ラジアン） |
| 実機へ送るとき | そのまま | **変換が必要** |

模倣学習は、人が操縦したときの**サーボの生の数値**（0〜4095の整数）を記録し、
サーボの数値を出力するように学習する。シミュレータの座標系を一度も経由しない。
**だから変換の誤りが入り込む余地がない。**

強化学習はそうはいかない。シムの中は**メートルとラジアン**、実機は**カウント**。
対応づける式が要る。

```
サーボ値 = 基準値 + 符号 × (シムの角度 − 既定角度) × 係数
```

この式には3つの数が要る。

| | 意味 | 決め方 |
|---|---|---|
| 係数 | カウント↔ラジアンの比 | 数学的に決まる（4096 ÷ 2π） |
| **符号** | 回転の向きが同じか逆か | **実機で測るしかない** |
| **基準値** | シムの原点に対応するサーボ値 | **実機で測るしかない** |

**この翻訳層が、強化学習だけが背負う難所だった。**

---

## 見つかった7つの誤差

一度に1つずつしか見えなかった。潰すと次が出てくる。

### ① 基準値に、まったく無関係な値を使っていた（56mm）

`SERVO_AT_DEFAULT`（シムの原点に対応する実機の値）に、
**`HOME_POSITION` をそのまま流用**していた。

作業メモには、HOME値の根拠がこう書かれていた。

| 関節 | HOME値 | 備考欄 |
|---|---:|---|
| shoulder_pan | 1505 | 「25度ズレ補正済み」 |
| shoulder_lift | 2242 | 「+10度が最適」 |
| elbow_flex | 1400 | **「アプローチ感」** |
| wrist_flex | 2375 | 「+30度」 |

**4つとも、模倣学習のタスク用に人が感覚で調整した値だった。**
シミュレータの原点とは何の関係もない。それを原点として使っていた。

コードには `【仮定】実機のHOME姿勢 = シムの default_joint_pos とみなす` と
コメントが残っていた。**書いてあったのに、誰も確認しないまま数週間使われた。**

実測した結果。

| 関節 | HOME値 | 実測した基準値 | 差 |
|---|---:|---:|---:|
| shoulder_pan | 1505 | **1409** | −96 |
| shoulder_lift | 2242 | **2197** | −45 |
| elbow_flex | 1400 | **1210** | −190 |
| wrist_flex | 2375 | **2044** | −331 |

**同じ指令に対する手先位置の解釈が、56mm ずれていた。**

### ② 回転の向きが2関節で逆だった

ロボットの形状定義ファイル（URDF）を読むと、6関節すべてが
`axis="0 0 1"`（Z軸回り）と書いてある。**しかし実際の回転軸は違う。**

| 関節 | URDFの表記 | 実際の軸 |
|---|---|---|
| shoulder_pan | `0 0 1` | **[0, 0, −1]** ← 逆 |
| shoulder_lift | `0 0 1` | [0, +1, 0] |
| gripper | `0 0 1` | **[0, −1, 0]** ← 逆 |

各関節は「原点の回転（rpy）」も持っており、`shoulder_pan` には180度の反転が入っている。
**`+Z` と書いてあるのに実際は `−Z` 回りに回る。**

> URDFの `axis` は、そのジョイント固有のフレームでの軸。
> 世界座標での向きではない。**読んでも分からない。行列を掛けるしかない。**

### ③ 爪が上下に開いていた（90度）

位置を5mmまで詰めても掴めない。

実機の前に立っている人に聞いた。

> **「2本の爪は、キューブの左右両側に来ていますか」**
> 「上と下」

**爪が上下に開いていた。** 机の上のブロックを左右から挟めない。

原因は `wrist_roll`（手首をひねる関節）の基準値が**90度ずれていた**こと。
この関節だけ最後まで未検証で残っていた。理由がある。

**手首ロールは、回しても手先の位置がほとんど動かない。**
だから高さや水平位置をいくら測っても検出できない。
唯一の見つけ方は「**爪がどちらに開いているかを人が見る**」ことだった。

なお私はこの計算を一度間違えた。**回転軸の向き ≠ 爪が開く向き**である。
爪は軸の**まわりに**回るので、開くのは軸に**垂直な面内**。逆に解釈していた。

### ④ サーボの積分ゲインが、全関節ゼロだった

肘に指令を出しても、**自重に負けて手前で止まる**。

| 指令 | 実測 | 不足 |
|---|---:|---:|
| 1406 | 1502 | 96 |
| 1340 | 1491 | **151** |
| 1554 | 1586 | 32 |

しかも負荷によって変動する。肩を17mm持ち上げても、
肘が同じだけ沈んで**正味ゼロ**という場面もあった。

「トルクが足りない」と思い込んでいた。**違った。**

サーボの制御レジスタを読むと、こうなっていた。

| 関節 | P_gain | I_gain | MaxTorque | TorqueLimit |
|---|---:|---:|---:|---:|
| M1〜M4 | 16 | **0** | 1000 | 1000 |
| M5 | 32 | **0** | 1000 | 1000 |
| M6 | 16 | **0** | **500** | **500** |

**トルク上限は最大値のまま。** 出せるトルクを出す指示がなかっただけだった。

**比例制御だけでは、重力のような一定外乱に必ず定常偏差が残る。** 制御の教科書どおりの現象。
積分項がその定常偏差を消す役割を持つが、それがゼロだった。

肘（M3）のゲインだけ変えた結果。

| 設定 | 肘の定常偏差 | 手先への影響 |
|---|---:|---:|
| P=16, I=0（出荷時） | 119 カウント | 約20 mm |
| P=32, I=0 | 40 | 約7 mm |
| **P=32, I=8** | **10** | **約2 mm** |

**10分の1以下。** 副次効果として、それまで必ず失敗していた
HOME復帰が、初めて全関節±14カウント以内で成功した。

#### そして、同じ誤りを3回に分けて潰すことになった

このとき直したのは**肘（M3）だけ**だった。その後グリッパー（M6）を直し、
**残る M1・M2・M4 は手つかずのまま2日間気づかなかった。**

| | 変更前 | 最終 |
|---|---|---|
| P | [16, 16, **32**, 16, 32, **32**] | [32, 32, 32, 32, 32, 32] |
| I | [0, 0, **8**, 0, 0, **8**] | [8, 8, 8, 8, 0, 8] |

肩（M2）を直したときの効果が大きかった。

| 関節 | 修正前の追従誤差 | 修正後 |
|---|---:|---:|
| **M2 shoulder_lift** | **+34**（再指令すると +32 → +34 と悪化） | **+1** |
| M4 wrist_flex | +15 | −1 |
| M1 shoulder_pan | −5 | −1 |

肩の34カウント（3度）は、到達230mmでは**手先で約12mm**になる。

そしてこれが、それまで説明できなかった現象の正体だった。
**「モデルの誤差が、姿勢によって −14.9mm から −23.7mm へ変わる」。**
一定のオフセットでは補正できず、バックラッシュや部品のたわみを疑っていた。
実際は**肩が負荷に応じて垂れていた**だけだった。

### ⑤ 掴む点の定義が30mmずれていた

> 「オブジェクトの30mm上空でつかんでいる」

URDFは `gripper_link` から98.4mm先を把持点（`gripper_frame_link`）としているが、
**実際に爪が挟まる点はそれより約30mm手前**だった。

逆運動学の目標を「先端から進行方向に30mm戻した点」に補正した。

### ⑥ 握力が足りない

ここまでで、爪はブロックに届き、両側から挟むようになった。
**しかし持ち上がらない。** 触れているだけ。

グリッパーのサーボだけ、トルク上限が **500**（他は1000）。制御ゲインも `P=16, I=0`。

トルク上限を上げるか迷ったが、**まず制御ゲインだけ**にした。
上限500は保護設定であり、このグリッパーは一度脱落事故を起こしている。

| | P | I | TorqueLimit |
|---|---:|---:|---:|
| 変更前 | 16 | **0** | 500 |
| **変更後** | **32** | **8** | **500（据え置き）** |

**これで掴めた。** トルク上限は上げずに済んだ。
「力が足りない」のではなく、**出せる力を出す指示がなかった**——肘とまったく同じ構造だった。

### ⑦ 爪のどこで挟むかが、成否を決めていた

掴めた。しかし**次の日、同じことをやっても掴めない。**

位置の誤差は1〜4mmまで詰めた。爪の傾きも変えて試した。
ブロックの位置を測り直し、逆運動学を解き直し、6回やって6回とも失敗した。

手がかりは、**グリッパーが閉じきらずに止まる位置**にあった。

指令は毎回 `2150`。しかし実際に止まる位置が違う。

| 止まった位置 | 結果 |
|---:|---|
| 2162〜2168 | 空振り |
| 2254 | 触れるだけ、力が弱い |
| **2196** | **成功** |
| 2498 | 持ち上げ途中で落下 |

**これは「ブロックが爪のどこに入っているか」を示していた。**

爪は先端に向かって狭まる形をしている。だから**奥に入れるほど、爪は開いた位置で止まる**。
そして先端は、てこの比が悪い。同じモータートルクでも挟む力が弱くなる。

つまり**深すぎても浅すぎても駄目**で、中間に適正値がある。それが 2196 だった。

2回目の成功も、**停止位置は 2196 ちょうど**だった。

> **サーボの数値ひとつで、把持の成否が事前に判定できる。**
> 目で見なくてよい。自律動作なら「握る → 停止位置を読む →
> 範囲外なら開いて高さを変えて再試行」という閉ループが組める。

位置精度をいくら上げても届かなかった理由が、ここにあった。
**測っていた量（位置）が、効いていた量（深さ）ではなかった。**

## 測り方で工夫したこと

### 定規で測れる

特別な装置は要らない。**URDFから各関節軸の高さを計算し、
テーブル面から定規で測って突き合わせる。** アームを動かす必要もない。

根元から順に測ると、**どこで誤差が入るかが特定できる**。
実際、肘の軸までは予測と±5mmで一致し、その先が一斉に45〜60mm低かった。

### ★一度、測り方を間違えた

高さを8点測って当てはめ、「較正できた」と考えた。**誤りだった。**

**高さは水平方向を拘束しない。** 当てはめは「高さが合う」パラメータを見つけたが、
水平は **56mm ずれたまま**だった。高さだけ完璧に合い、水平だけ大きく外れる——
不自然に見えて、実は当然の帰結だった。

較正済みカメラで**水平位置を1点測って加えた**ところ、4関節すべてが決まった。

> 3次元の対応づけを、1方向の測定だけで検証してはいけない。

### 「右」「左」と言わない

向きの確認で何度も混乱した。「カメラから見て右」なのか
「ロボットから見て右」なのか、言葉では決まらない。

そこで**言葉を使わない方法**にした。

1. 動かす**前**のカメラ画像と全関節の数値を記録
2. 「**どちらでもいいので**その関節だけ大きく動かして」と依頼
3. 動かした**後**の画像と数値を記録
4. **どちらへ動いたかは、画像を見る側が判断する**

視点の食い違いが原理的に起きない。

### 印ではなく輪郭を描く

ブロックの位置を記録するとき、点で印をつけると**14mmずれた**。

カメラの変換はブロック中心の高さ（20mm）で較正してある。
**テーブル面（0mm）の印を同じ変換で読むと、系統誤差が入る。**

**底面の輪郭をなぞる**方式に変えた。輪郭は「ブロックをはめる型」としてしか使えないので、
誤って座標を測ることがない。**座標は常にブロックを置いて測る。**

### 照明で精度が変わる

逆光のとき、検出面積が **3085 → 1191** に落ち、位置が **8mm** ずれた。
照明を点けると面積が戻り、位置も安定した。

NVIDIA の Sim-to-Real 教材が「ライトボックス」を要求する理由が、実地で分かった。

## 連載を貫いている一本の線

書いていて気づいた。**(4)(5)(6)と今回、原因はすべて同じ形をしている。**

| 記事 | ずれていたもの | 規模 | 気づくまで |
|---|---|---|---|
| (4) | カメラの**位置** | 数cm | — |
| (5) | カメラの**向き** | **90度**＋被写体が写っていない | 300エピソード生成後 |
| (6) | カメラの**視点**（データ内で混在） | — | **6か月** |
| (7) | **サーボの基準値** | **56mm** | 1週間 |
| (7) | **爪の向き** | **90度** | 1日 |

**90度のずれが2回**出ている。(5)ではカメラ、今回は手首ロール。
どちらも「**見れば一目で分かるが、数値だけ見ていても永久に気づかない**」種類の誤りだった。

そして記事(6)の原則は、そのまま今回に当てはまる。

> 収集環境と評価環境を一致させ → **シムと実機の基準を一致させ**

対象が変わっただけで、構造は同じだった。

## この経験から言えること

### パイプラインが動くことと、正しいことは違う

検出も推論も送信も同期も、すべて「動いて」いた。ログにもエラーは出ない。
**それでも掴めなかった。** 入力の数値が間違っていたから。

### 指標が誤りを検出できないことがある

同期制御の「追従誤差16〜35カウント」を品質指標として見ていた。
しかしこれは**「サーボが指令値に到達したか」**を測る指標で、
**符号が逆でも実機は逆向きの指令に忠実に追従する**。
**指標が構造的に盲目だった。**

### 根拠のない前提は、いつか必ず効いてくる

`SERVO_AT_DEFAULT = HOME_POSITION` は、誰も検証していなかった。
コードにも「【仮定】」と書いてあった。**書いてあったのに、確認されなかった。**

### 測る対象を間違えると、測らないより危険

高さ8点という「充実した測定」をして、較正できたと判断した。
**測っていない方向に、56mmの誤差がそのまま残っていた。**

### 実機の前にいる人が、いちばん正確に見ている

私（AI）は画像から爪とブロックの位置関係を何度も読み違えた。
一方、実機の前にいる人の観察——**「爪は上下」「30mm上空」**——は、
いずれも一言で核心を突いた。

**遠隔の計算と、現場の目は、役割が違う。**

## 現在地

| 項目 | 状態 |
|---|---|
| 座標変換の基準値 | ✅ 56mm → 5〜7mm |
| 回転方向の符号 | ✅ 2関節の誤りを修正 |
| 爪の向き | ✅ 90度を修正 |
| サーボの追従 | ✅ 20mm → 2mm |
| 掴む点の定義 | ✅ 30mm補正 |
| 握力 | ✅ 制御ゲインで解決（トルク上限は据え置き） |
| 全関節の追従 | ✅ 誤差±1カウント |
| **把持** | ✅ **成功・再現も確認** |
| カップへ運ぶ | ⬜ カップの位置を測る仕組みがない |
| 学習したポリシーの実行 | ⬜ **未着手** |

**「なぜ届かないか分からない」から「掴んで持ち上げられる」まで来た。**

そして本題——**シミュレータで学習した方策を実機で走らせる**——は、まだ一度も試していない。
今回やったのは、その試行を**意味のあるものにするための下準備**だった。

翻訳層が間違っていれば、どんなに優れた方策でも実機では動かない。
9月8日の時点でパイプラインは全段機能していた。それでも掴めなかったのは、
**誰も測っていなかった6つの数値**のせいだった。

## 使った道具

| 道具 | 用途 |
|---|---|
| **定規** | 関節軸の高さ。特別な装置は不要 |
| **較正済みカメラ**（誤差9.1mm） | 水平位置 |
| **URDF から自作した順運動学** | 予測値の計算。1秒で動く |
| **サーボのレジスタ読み出し** | 制御ゲインの発見 |

Isaac Lab を順運動学の計算機として使うこともできるが、**起動に数分かかり、
一度15分ハングした**。URDF を直接読んで行列を掛ければ**1秒**で同じ答えが出る
（Isaac Lab の出力と差分0.98mm以内で一致を確認）。

## ★決着：キューブ配置のバリエーションは「ほぼ存在しなかった」

較正やホモグラフィを使わず、**キューブ自身（実寸4cm角）を定規にして**画像から直接測った（`~/measure_cube_spread.py`）。31本すべてで検出成功。

| 測定 | 値 |
|---|---|
| 横(px)の散らばり | 幅40px = **2.8cm** / 標準偏差 7.2px = **0.5cm** |
| 奥行(py)の散らばり | 幅44px = **3.1cm** / 標準偏差 8.3px = **0.6cm** |
| 参照 | ブロック実寸 4.0cm角（見かけ58.0px → 0.0690 cm/px） |

**31本すべての配置がブロック自身より小さい範囲に収まっている**（重ね描き図 `~/cube_placements.png` で、31点の凸包がブロックの内側の薄い線になる）。検出は目視確認済みで正常（`~/diag_cube_detect.py`、赤輪郭が全フレームで木製ブロックに一致）。

### 含意

- 「スイートスポットが狭い」のではなく、**学習データに配置バリエーションが最初から無かった**。31ep / 16,149フレームすべてが実質同一の置き位置。
- **Cosmosで空間カバレッジが広がらなかったのは当然**——広げる元が無かった。見た目の多様化しかしていないので原理通り。
- **左右非対称（右は広がり左はダメ）は配置分布では説明できない**（分布自体が存在しない）。別の要因＝運動学的な到達性、モデルの外挿の癖、カメラの遠近など。
- **対策は単純明快**：帯域を計算するのではなく、**ブロックを意図的にばらして録り直す**。現状が実質1点なので、どこに置いても新規カバレッジになる。

### 前版からの訂正

前版の「キューブ配置は標準偏差78カウント（約7°）の狭い帯」は、**pan角（関節値）から間接的に推定した値**だった。画像から直接測った上記が正しい。「配置を散らして録り足す方向は正しい」という結論自体は変わらない（むしろ強化された）。

なお、その前段でも誤りがあった。**「グリッパー最小値＝掴んだ瞬間」という判定が間違っていた**——実測すると最小値はエピソードの平均72%地点＝運搬中またはカップ上で発生する。旧分析の「掴み位置が密集」はカップの方向を測っていた。

> 教訓: **数えるのは推測より確実だが、何を数えているかを間違えると推測より危険**。

## 今やるべきこと

**実機で1関節ずつ動かし、raw値の増減と物理的な動く向きを記録する。** これ一つで複数の詰まりが同時に解ける。

理由は、**両トラックが同じ測定を待っている**から。`MOTOR_LIMITS` の再定義が「高優先・両方」であり、「正しい機械端はトルクOFFで手で動かして記録するしかない」。関節中心値で詰まっているのも同じ測定。

手順:

1. フォロワーのトルクを外す（`~/release_torque.py`、作成済み）
2. 1関節ずつ機械端まで手で動かし、raw値を記録 → `MOTOR_LIMITS` の正しい値
3. 同時に「raw値が増えると物理的にどちらへ動くか」を記録 → 関節の符号と中心値
4. これで**シムと実機の座標系が初めて一本に繋がる**

**並行して可能**（実機不要）:

- ブロックを散らした追加録画の設計（現状が1点なのでどこでも新規カバレッジ）
- `so101_dataset_v6_lang35` での言語条件付け学習（GPUは空いている）
